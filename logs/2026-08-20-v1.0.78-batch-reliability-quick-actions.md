# v1.0.78 — Batch Reliability + Quick Actions Layout

Date: 2026-08-20

## User-reported problems

The batch UI was repeatedly showing failures such as:

- `Error: network error`

while processing several videos sequentially.

The screenshots also exposed a second usability issue:

- after choosing a single video, the user had to scroll through preview, Detect and Tune sections before reaching `Clean video` near the bottom of the page.

A third concrete defect was confirmed in the existing batch retry implementation:

- `Retry` was visible on a failed row while the rest of the batch was still running;
- `retryItem()` immediately returned whenever `state.running === true`;
- the legacy `batchRetryFix.js` fallback attempted to click `Clean all`, but `Clean all` is disabled while the batch is active;
- therefore Retry could visibly be clicked yet do nothing during the most common failure state.

## Scope

v1.0.78 is a reliability/UX release.

It does not change watermark detection thresholds, alpha calibration, reconstruction strength, structured cleanup strength, center-seam/local-tone/outer-halo processing, smooth-background reconstruction, or final cleaned pixel policy.

## Root-cause analysis: intermittent network/worker failures

Before v1.0.78, `src/batch-ui.js` created a brand-new module Web Worker for every batch stage:

1. create worker for Inspect;
2. terminate it when Inspect completes;
3. create another worker for Process;
4. terminate it when Process completes;
5. repeat twice per video across the queue.

For seven videos this can create fourteen separate module-worker startup cycles, each requiring the browser/runtime to instantiate the worker module graph again.

In a browser session backed by a development server, Codespace, Pages deployment, unstable connection, cache miss, or transient module fetch interruption, this unnecessarily increases exposure to `network error`, module-load, worker-transport and fetch failures.

The worker itself already resets adaptive processing state at the start of every Inspect/Process request, so a worker does not need to be destroyed after every successful stage.

## Batch worker lifecycle change

`src/batch-ui.js` now reuses one persistent batch worker across the sequential queue.

New behavior:

- create the worker lazily on the first batch task;
- reuse the same worker for Inspect and Process;
- reuse it for subsequent files;
- keep per-request tag isolation;
- attach temporary message/error listeners for the active request only;
- terminate/recreate the worker only when a worker transport/module error occurs or when the page unloads.

This reduces repeated worker-module loading and should materially reduce intermittent module/network startup failures during larger batches.

Sequential processing is preserved to keep memory pressure bounded.

## Automatic transient retry

Added:

- `src/batchWorkerReliability.js`

The module classifies only transport-like errors as transient, including common forms such as:

- `network error`
- `NetworkError`
- `Failed to fetch`
- module-script loading errors
- worker transport failures
- connection reset/closed/lost

It deliberately does not retry normal logical processing failures such as:

- detection confidence below the configured threshold
- user cancellation (`AbortError`)
- ordinary non-network algorithm errors

### Retry limit

A transient worker/transport operation receives at most two automatic retries after the original attempt.

Backoff:

- retry 1: 220 ms
- retry 2: 440 ms
- hard delay cap: 1400 ms

Before retrying, the possibly unhealthy worker is terminated and a fresh worker is created for the next attempt.

The affected batch row reports a reconnecting status instead of immediately becoming red/error.

## Output-folder save retry

File System Access output writes can also surface transport-style `NetworkError` conditions in some browser/filesystem environments.

v1.0.78 therefore gives a matching transient output save one bounded retry.

Non-transient save errors are still surfaced normally.

## Manual Retry defect fix

The direct `retryItem()` behavior was rewritten.

### Old behavior

`Retry` returned immediately when `state.running` was true.

That meant a failed earlier video could not be requeued while later videos were still processing.

### New behavior

When Retry is clicked on an Error/Cancelled item:

- the item is reset to `QUEUED`;
- its old detection/error state is cleared;
- if the batch is idle, processing resumes immediately;
- if another file is currently running, the item becomes `Retry queued`;
- `state.rerunRequested` is set;
- after the active item finishes, the current queue loop yields and starts a fresh queue pass;
- because the retried file retains its original list position, an earlier failed item is prioritized before later waiting rows on the resumed pass.

This makes Retry functional even while another video is processing.

## Quick actions layout

Updated:

- `src/batch-mount.js`

The single-video Export panel is moved directly below the existing video chooser panel at runtime.

New top-level order becomes approximately:

1. Choose/drop single video
2. Quick clean / Export
3. Batch Processing
4. Preview
5. Detect / Tune diagnostics
6. Result preview

The Export heading is renamed at runtime to:

- `Quick clean / Export`

This keeps the most frequent workflow near the top of the page:

- choose video
- wait for automatic detection
- click Clean video
- cancel/download as needed

The user no longer needs to scroll through the full diagnostic/tuning section just to find `Clean video`.

The Batch Processing panel is mounted immediately after the Quick clean / Export panel.

## Batch UI note

The batch note now explicitly states that:

- processing remains sequential;
- one worker is reused across the queue;
- transient worker/network failures are retried automatically before a file is marked failed.

## Regression tests

Added:

- `tests/batchWorkerReliability.test.mjs`
- `tests/quickActionsLayout.test.mjs`

Coverage includes:

1. `network error` is transient;
2. module/fetch failures are transient;
3. explicit worker transport errors are transient;
4. detection-confidence failures are not transient;
5. AbortError is never automatically retried;
6. retry count is bounded at two retries;
7. retry backoff is short and capped;
8. Quick clean / Export is moved directly after the chooser panel;
9. Batch Processing is mounted after Quick clean / Export.

Existing batch tests remain responsible for queue status, file picker stability, and legacy Retry integration compatibility.

## Pixel-safety statement

No video-cleaning algorithm parameter is changed in this release.

The batch reliability changes affect worker lifetime, transient retry and queue scheduling only.

3. `npm run check`
4. complete `npm test`
5. `npm run build`

Do not merge until the actual workflow is observed green.

## Post-merge validation checklist

### Batch reliability

Use at least 7 videos, matching the user-reported screenshot scale.

Verify:

- no repeated worker/module network error under normal operation;
- if a transient network error is intentionally/reliably reproduced, row status shows reconnecting and automatically retries;
- a persistent error is eventually shown after bounded retries;
- Retry on a failed earlier row works even while a later row is processing;
- retry does not create duplicate output rows/files unexpectedly;
- Cancel batch still cancels the active worker task.

### Quick action UX

Verify on desktop and narrow/mobile width:

- Choose video remains at the top;
- Quick clean / Export appears directly below it;
- Batch Processing follows;
- Clean video is reachable without scrolling through Detect/Tune diagnostics;
- existing Detect/Tune controls still operate normally lower on the page.

## Remaining risk

A `network error` can originate from browser/platform components outside the worker startup path. v1.0.78 reduces the known repeated-worker-load exposure and adds bounded recovery, but real batch testing is still required to establish whether the user's exact environment has any additional source of transport failure.
