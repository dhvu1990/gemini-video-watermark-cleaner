### Root cause

The failure was unrelated to the center-seam algorithm. `tests/windows-launcher.test.mjs` still contained a hard-coded assertion for the previous release:

```js
assert.match(version, /export const APP_VERSION = '1\.0\.42'/);
```

After the intended v1.0.43 version bump, `src/version.js` correctly contained:

```js
export const APP_VERSION = '1.0.43';
```

Therefore the shared-version-source regression test itself became stale.

## Fix

The runtime-version test now derives the expected version from `package.json` instead of hard-coding a release number.

New strategy:
1. read and parse `package.json`;
2. escape the current `packageJson.version` for use in a regular expression;
3. assert that `src/version.js` exports the same value;
4. retain the existing checks that the UI and worker import `APP_VERSION` from the shared source.

This preserves the original purpose of the v1.0.38 source-of-truth test while removing a manual update point that can fail on every future version bump.

## Versioning decision

Project policy requires every new repository edit batch to advance the version rather than silently modify an existing release candidate. Because this CI repair changes repository content after v1.0.43 Phase 1, the branch is advanced to **v1.0.44**.
