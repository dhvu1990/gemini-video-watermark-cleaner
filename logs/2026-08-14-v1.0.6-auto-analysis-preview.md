## Performance analysis

The previous detector already ran inside a Web Worker, so moving the same work to a Worker again would not solve the whole responsiveness problem.

Two avoidable costs were identified:

### 1. Detection metadata was computing export-only packet statistics

`metadataOf()` always called `track.computePacketStats(90)` even during watermark inspection. Packet-rate and bitrate statistics are useful for export/frame-count estimation but are not required to locate a watermark.

v1.0.6 changes metadata resolution so normal detection skips packet statistics. Full packet statistics are requested only when the export path needs them.

### 2. Reducing frame count alone does not make a quick scan truly quick

A naive 4-frame scan spread across the whole video still requires sequential decoding toward the end of the video. It lowers retained frame memory but can still walk through most of the stream.

v1.0.6 therefore adds a **progressive scan policy**:

- quick scan: 4 sampled frames,
- quick scan range: first 25% of the video duration,
- stricter quick acceptance threshold: at least `max(0.20, minConfidence + 0.06)`,
- quick vote ratio: at least 0.5 when available,
- if the quick result is insufficient, automatically run the configured full scan (12 frames by default) across the full duration.

For the reported test video, the previous full detector confidence was around 0.868, so the expected path is that the new quick scan will usually be accepted without needing the full fallback. This expectation must still be verified in the deployed browser using the same real file.

## Preview implementation

v1.0.6 adds a new preview panel immediately below the file selector.

### Full-frame preview

The browser displays the local video via an object URL with `preload="metadata"`.

The detector returns video dimensions and the detected watermark position. The UI converts the detector coordinates to percentage-based overlay coordinates and draws a bounding box over the video preview.

No full 1080x1920 image buffer is transferred from the Worker back to the main thread for this preview.

### Zoomed Original / Cleaned preview

The Worker retains the sampled frames needed for detection. After detection it selects a representative sampled frame and crops only the detected watermark ROI.

The Worker returns two small typed-array image payloads:

- `original`: detected ROI from the sampled frame,
- `cleaned`: the same ROI after inverse-alpha restoration plus edge polish.

For a 72x72 watermark this is only about 20 KB of RGBA data per preview image, instead of transferring an entire multi-megapixel frame to the main thread.

The browser renders these into two canvases:

- **ZOOMED ORIGINAL**
- **ZOOMED CLEANED**

## UX changes

- File selection automatically schedules the detector after the browser has had an opportunity to paint the selected-file state.
- The initial detector is a progressive quick scan.
- If quick confidence is high enough, the result is shown immediately.
- If quick confidence is insufficient, the UI explicitly says that analysis is expanding and starts the full scan automatically.
- The old **Analyze watermark** button is renamed to **Re-analyze full video**.
- The technical JSON detector result is retained for debugging, but the visual preview becomes the primary result.
- The preview shows whether the bounding box is a confirmed detection or only a low-confidence candidate.

## Export optimization

Before v1.0.6, clicking **Clean video** after a successful analysis could cause the engine to run watermark detection again internally.

v1.0.6 sends the already reviewed detected region back to the Worker as `detectedRegion` and reconstructs the appropriate alpha map by detected size. The export path still performs per-frame confidence gating, adaptive alpha, edge polish, temporal stabilization, audio passthrough, and scene-cut handling, but it does not repeat the full multi-frame position search unnecessarily.
